## Phase 5 verification — scenario questions & answers

- **Q (stale-gate):** "An incident you re-fired rolls back instantly with no new operator decision — walk me through the mechanism and the fix." **A:** the GateAwaiter keys futures by `incident_id`; a re-run found the previous run's *already-done* future, so `resolve` returned False (`already_decided`) and the driver resumed with the old decision — 16.3 ms gate→rollback, no `Operator decision` event. `run_once` now calls `reset(iid)` first, parking a fresh future per run, and `wait()` stays idempotent so the fast-click path and older tests still resolve before the driver resumes. Proof: live re-fire parks at GATE OPEN and requires a brand-new decision.
- **Q (shutdown-hang):** "Why did `SIGTERM` get ignored, and what specifically changed?" **A:** redis-py's `async_timeout` swallows uvicorn's injected `CancelledError` mid-`brpop` and re-raises it as `TimeoutError`; the old generic except spun right back into `brpop`, so the lifespan's `await task` never completed. The loop now owns a `shutdown_event` re-checked after every item *and* every fetch failure, `CancelledError` still propagates, and the lifespan caps the await at 10 s — measured clean stops on real servers since.
- **Q (human-gate NG-1):** "Prove the gate is a human, not a fallback." **A:** exactly two call sites send a decision — the GatePanel Approve/Reject buttons (`useSocket.decide`); no timeout/auto-decision exists anywhere in `app/` or the frontend. The driver *parks* (`await wait(iid)`), the §5.4 handler only resolves the future, and the driver stays the single writer on the checkpoint — no two tasks can resume the same run.
- **Q (queue honesty):** "The footer and the `QUEUED behind` banner both derive from the same `/api/status` snapshot, polled every 3 s. What is the source of truth that can never lie, and what happens if the poll stalls?" **A:** the WebSocket stage-event stream — each event is published by the pipeline itself, so the timeline is honest even when the status snapshot is stale. If the poll stalls, the footer/banner freeze on the last truth (the named blocker read stays correct), but every event still streams and the gate still resolves — status is an aid, never a claim: stale, not wrong, and the next poll self-corrects. Verified in-session: banner appears exactly while `gates_waiting` names a different incident and the fired run has no stage past `ingest`, and clears the moment the run starts.
- **Q (T-7.7 timing honesty):** "A run parked at the gate for 22 minutes gets approved, and the terminal row reports `resolved · 22 min`. Would the timeline lying about *which* stage took that time pass your review?" **A:** no — before the fix it *did* lie: the rollback stage inherited the operator's wait because `_t_chunk` was last set at the pre-park chunk, so the resume's first chunk claimed the whole human wait as "rollback took 22 min". The driver now restarts the stage clock at resume, so the run's total (honestly including the human wait, carried by `done.t_resolve_ms`) is never mis-attributed to a post-gate stage; the regression test simulates a 0.5 s decision wait and asserts the rollback stage reports < 200 ms. The remaining honesty boundary is `done.t_resolve_ms` — it includes gate time *by design* (end-to-end resolve latency), and the timeline labels it as resolve total, not per-stage.
- **Q (T-7.8 watchable rehearsal):** "An operator fires an incident in smoke mode and the timeline fills instantly. You add a 1-second sleep in the smoke classifier. An engineer objects: 'you're faking latency.' Defend the change, or change it." **A:** the objection is half-right but the conclusion is wrong. The sleep never fabricates *output* — the evidence, plan, and classification are the same deterministic fixtures the smoke mode already agreed to produce; those were always rehearsal data, labeled SMOKE. What changed is *delivery*: an un-paced rehearsal finishes in one frame (<100 ms), which reads as a pre-recorded script and denies the operator the one thing they asked for — watching the system think. The `stage_duration_ms` stamps are honest because they measure the stream the operator actually watched (the paced fakes really do take that long). Two guardrails keep it honest: the pacing lives only in the console's graph build (`run_console --smoke`), so the benchmark's real recurrence timing is never affected, and `NEXUSOPS_SMOKE_PACE=0` restores instant mode for anyone who wants it. Delivering the same true data more slowly is a presentation choice; presenting slowed data as if it were fresh is the fabrication — and we did neither.
- **Q (T-7.9 real-mode retry):** "You added a retry wrapper to the console's real graph. A reviewer says: 'the whole point of D-6 is that a down model degrades to manual_review — your retry hides that the model is down.' Defend the change, or change it." **A:** the retry and the degrade serve different truths and both stay intact. `_retry_model` only retries errors the provider itself marks as transient (`retryable=True`: 429/5xx/timeouts) and stops at a provably-capacity-limited class (`_quota_exhausted` → non-retryable → raises immediately, which is what happened to the 2026-09-22 judge run). A momentary `503 high demand` during a live console demo is not "the model is down" — it's a queue ball, and converting it into a permanent `manual_review` would teach the operator the wrong mental model. The final attempt still raises, so a genuinely down model still reaches D-6's honest degrade — just not on the first bad luck. The guardrail is the boundary: retry transient, never retry quota/broken-contract, and the regression test pins both sides.
- **Q (T-7.10 stepper honesty):** "An incident degrades to `manual_review` during classify. What did the pipeline stepper show before your review, and what does it show now — and where exactly does the live 'waiting 42 s' number come from?" **A:** before, the first implementation forced `Gate ✓` whenever any terminal arrived and lit `Resolve ✓` on the `done(manual_review)` event — so an aborted run that never opened a gate and executed nothing rendered two green checkmarks, visually claiming an execution that never happened. Now gate is done **iff** a real operator `decision` exists and resolve is done only on a non-`manual_review` terminal; `failedAt` dashes every step after the failure, so the honest frame is `Classify ! → – – –`, readable as "aborted before the gate" at a glance. The live elapsed comes from `_arrived_ms` — the client's own `Date.now()` stamped at WS receipt in `useSocket` — so "waiting 42 s" is what the operator literally observed, never a server claim of model latency; completed step marks come only from the server's `stage_duration_ms`/`t_resolve_ms`. Two clocks, two honest labels, never mixed in one cell.
- **Q (T-7.11 rca config):** "`/api/status.rca_model` is a single string, but the default RCA choice is per-path — frontier for escalated incidents, SLM otherwise. How does the operator tell which model actually wrote a given plan?" **A:** the status row is the **configuration snapshot** (which model family was selected at launch); the **runtime truth is per-event** — the `plan` event's `model_env` names exactly the model that wrote that plan (frontier when a default run escalated, SLM under `--slm-rca`), `classified` carries its own SLM stamp, and `escalating.depth_model` states which model will do the deep-dive that follows. Both the node and the stamp read one env, so a stamp can never name a model that didn't write the plan; the state-machine spy asserts which env the node hands the model fn and the driver test asserts the stamps + status agree under both override and default — if someone ever rewires only one side, the suite fails loudly.
- **Q (T-7.12 reader-facing reason):** "A reviewer reads a `manual_review_reason` that says `SLM classify failed (quota): You exceeded your current quota...` and asks: 'you are leaking provider error JSON to the operator — why not a friendly 'model unavailable, sorry'?'" **A:** because a friendly lie is exactly what produced the bug being fixed. The live report was *"model error" on every call* — that string masked three distinct truths: transport flap (goes away on retry — the D-13 wrapper handles it), quota exhaustion (terminal — retrying burns the free day, 2026-09-22 postmortem), and contract breakage (a real bug). The operator who must decide whether to keep demoing needs the CLASS (quota = stop now; transport = it'll clear) and a detail that distinguishes them. `kind` is the structured class, the provider's own words are the evidence, and the sentence `stage failed (kind): detail` stays readable because `str(exc)` is never empty — when the provider says nothing, the cause's class name carries the story. This is the same honesty contract as B1 provenance: the operator is an adult, the console is not a PR page.
- **Q (T-7.13 where the reasoning lives):** "You put the model's WHY in the plan, the human's WHY on the gate, and the MCP raw records in the incident record — two reasoning lanes plus a data dump. An engineer argues the operator only needs the conclusion and the decision input. Where does each live, and why is splitting them more honest than combining?" **A:** three distinct speaker/ownership boundaries, never conflated. (1) The **model's reasoning** (`plan.reasoning`, required by `RCA_SCHEMA`) is the LLM's justification for *its* hypothesis — it lives on the plan event and renders at the gate because the human's decision input is *judging that argument*; showing hypothesis-without-reasoning at the moment of decision is how a bad plan slides through on confidence. (2) The **operator's reason** (`decision.reason`, optional, never required — NG-1 is the decision itself) is *their* judgement, stored on the resume body so the checkpoint archives it (audit: rollback + human rationale in one record) and published on the `decision` event for the UI; a blank string is a loud error, an absent key is a valid decision — prose must never gate execution. (3) The **evidence records** (`tool_call.evidence`) are the tools' raw output — the only lane that is data, not reasoning, which is exactly why it renders verbatim (never summarized by a model) in the incident record, so the operator can check a claim against the source at any time. Combining any two would let one speaker's words masquerade as another's: the plan event would carry the operator's decision, or a summarized evidence line would become the model's citation.
